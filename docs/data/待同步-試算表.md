## 🔴 未解問題一：`action=watch` 端點異常（新增監控公司寫不進去）

**症狀**：POST `action=watch` 一律回傳 **Google 的 HTML 頁面**（`<!doctype html>...ppConfig...`）
而非 `{"ok":...}` JSON。已試三種傳參方式，全部相同結果：

1. POST body JSON 內含 `"action":"watch"` → HTML
2. POST `?action=watch` 放 query string ＋ body JSON → HTML
3. GET 全部參數放 query string → HTML

**對照**：同一支端點的**事件寫入正常**（本輪 8 筆全部 `{"ok":true}`），
`?list=watch` / `?list=progress` **讀取也正常**——**只有 `action=watch` 這個動作壞掉**。

**佐證此為新故障**：試算表觀察名單最後三列為「聯光通」（9/15 新增）、
「創鉅材料」（9/17 新增）、「台灣固而美工業」（9/18 新增），
**代表 `action=watch` 在 9/18 當天還是好的**，故障發生在 9/18～9/19 之間。

**影響**：本輪新增的 1 家公司沒寫進試算表觀察名單。
`watchlist.json`（GitHub 端）已正常寫入，兩端出現落差。

## 🟡 已修正問題一：MOPS 去重鍵用錯欄位，**靜默吞掉一則監控區域重訊**

**症狀**：本輪自掃 MOPS 合併去重時，去重鍵誤用 `(COMPANY_ID, SEQ_NO, HEADING)`，
但 ezsearch 回傳的欄位是 **`SUBJECT`**（無 `HEADING`）、且 `SEQ_NO` 也不在回傳欄位中
——兩者取值皆為 `None`，**去重鍵實際退化成 `(COMPANY_ID, None, None)`**，
導致**同一家公司當日的多則重訊被併成一則**。

**實際損失**：玉山金 9/18 發了**兩則同主旨**的購置不動產重訊——
SEQ_NO=3 台中西屯福科路 3.75 億、SEQ_NO=4 新北中和 5.276 億。
**台中那筆（監控區域內）被靜默併掉**，是靠 C 線第 15 列交叉比對才發現。

**修正**：去重鍵改用 `(COMPANY_ID, SPOKE_DATE, SPOKE_TIME)` 或直接用完整 `HYPERLINK`
（`HYPERLINK` 內已含 `SEQ_NO`＋`SPOKE_TIME`，天然唯一）。**不可用主旨當去重鍵。**

## 🟡 已修正問題二：深研查詢 `RADIO_CM=1` 不依 `CO_ID` 過濾，且必然截斷

**症狀**：深研（查單一公司近一年重訊）若用 `RADIO_CM=1` ＋ `CO_ID`，
`CO_ID` **形同無效**——回傳的是全市場資料，且每個 30 天區間都撞上 **1000 筆上限而靜默截斷**。

**實際損失**：以此寫法查台化得 **13 則**，一度誤判「114/12/12 彰化 21 公頃處分案是未被系統掌握的新發現」，
實際上該案 8/12 即已建檔、9/07 已深研。

**修正**：深研一律用 **`RADIO_CM=2` ＋ `CO_ID`**，會真正依公司過濾且不截斷。
同一區間改正後得 **161 則**，**差距 12 倍**。

**症狀**：深研輪替規則為「依公司 md『最後更新』最舊優先」，

**兩家實際上分別在 9/15 與 9/07 剛做過深研**——輪替選到了最近才做過的兩家，

**本輪處置**：兩家的最後更新欄位已修正；深研對象改選**聯純科技**與**台灣固而美工業**
（皆為高分 A 級、從未深研、且有立即業務價值），兩家均已完成並產出實質成果。

**建議的永久修正**：輪替排序不要只看 md 欄位，改用
