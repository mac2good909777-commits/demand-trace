## 一、專案目標

追蹤中部（台中/彰化/南投/苗栗/雲林/嘉義）公司的經營軌跡——**購置、處分、產業鏈動態**——
交叉判讀真實意圖，在需求成形的最早時點切入：處分＝幫它賣、購置＝幫它找、產業鏈＝追交易對手。
Claude 角色＝監控員＋經營協作教練（每天回看 Mac 的經營進度並給下一步）。

## 二、核心方法論（Mac 定調，勿改）

1. **訊號時效權重：重訊 ＞ 新聞 ＞＞ 實價登錄**（同一事件以最早訊號源起算時效）
2. **時間軸模型**：重訊≈私契簽約 → 交廠 4個月~1年 → 公契(謄本原因發生日) → 過戶 → 再1-2月實價揭露
   （實證：環鴻購明基三豐精科廠，重訊114/08、過戶115/08/05）；交廠前3-6個月＝賣方安置需求高峰
3. **大宇範式**：處分≠經營不善，須交叉同期購置判讀（資產活化/產能重配置）；交易相對人一律追蹤
4. **注意力導向評分**：排序＝「今天該把注意力放哪」——已關注(active/有進度紀錄且無新事件) **-25**、
   新鮮未接觸(事件≤30天無紀錄) **+10**、新事件出現取消-25重新拉高。基礎分見排程 prompt
5. 公司md：重訊原文全文貼入（公開申報資料）；新聞只摘要＋連結（著作權）
6. **處分訊號的處理順序：先打電話、再查MOPS**（2026-08-10 和大實證）——
   `董事會決議處分` 的**決議日與委託決定通常是同一天**，真正的空窗不在決議後90天，而在**專任委託到期後**。
   和大查證花兩天且兩天皆失敗，電話花十分鐘就問出標的＋「已專任委託他家」（公告看不出來的通路狀態）。
   **查證與接觸應是同一個動作**（同理：頌勝一通電話同時解決查證與供件）。
   b類前兆（處分決議標的未明）的窗口意義一律以此重讀：**要問的不只是「賣什麼」，是「委託出去了沒」**。

## 十、分類系統與登入版架構（2026-08-13 新增，重要）

### 10.1 卡片分類（4 類）
每張公司卡片與 md 檢視都有「歸類」切換列（`catSwitch()`）：
- 💼 **重點經營**（focus）｜🔭 **長期追蹤**（track）｜🤝 **交易洽談**（deal，**owner-only**）｜🗂 **封存**（archive）
- 封存＝從「公司軌跡」清單移除；交易洽談＝從公司卡片點「設為交易洽談」進入（帶入該公司歷史），之後只有 owner 看得到。

#### 🤝 交易洽談的定義（Mac 2026-08-13 定調，**勿自行放寬**）
**＝我方對這家公司的經營，已推進到「正在談一筆具體的買賣／出租交易」。**
是**我方經營進度的階段**，不是「這家公司有沒有交易在洽談」——別拿重訊或公司動態去判斷。
- **算**：出價、議價、斡旋、簽約前條件談判、租金條件談判、雙邊代理促簽（有具體標的＋對象在談）
- **不算**：委託、帶看、供件、開發信、電訪、約訪、拜訪
- ⚠️ **委託不算**——最易誤標。拿到委託只是取得銷售權，桌上還沒有交易對象。
- 現況符合者：大統益×興國橡膠（廠地議約中近簽約・雙邊代理收斡促簽）。
  和大（已專任委託他家）、頌勝（供件）**不算**。
- 因此 **deal 必須純人工點選**：系統看得到重訊與進度紀錄，但看不出「這筆有沒有真的在談」。
- **分類來源**：由「經營進度」表的**標記字**決定，非寫在 watchlist。對照表
  `CAT_MARKS={'設為重點經營':focus,'設為長期追蹤':track,'設為交易洽談':deal,'追蹤結案':archive}`。
  `catOf(公司)`＝取該公司在進度表最新的一筆標記字；若無標記則回退 watchlist `active→focus`。
- **長期追蹤初始為空**：只由 Mac 或助理人工判斷加入（點「設為長期追蹤」）；**排程不得自動貼**。
- **`track` 與 `deal` 都只能人工標記，排程一律不得寫入**（deal 的理由見上方定義）。
- 事件時間軸：**新→舊**排序（新的在最上，`recordDate` 反向 localeCompare）。

### 10.3 登入版空白 bug 與修法（务必理解，否則會再踩雷）
- **症狀**：登入版整頁空白或永遠卡「載入中…」，但 github.io 公開版正常。
- **根因**：登入版 HTML 跑在 HtmlService 沙箱(googleusercontent) 內。沙箱中前端對 `script.google.com`（EP 的 `?list=progress`/`?list=needs`，即 loadProg/loadNeeds）的 fetch **會卡住而不 reject**→`Promise.all` 永不 resolve→`.then` 內的渲染與 tab6 揭示碼都不執行。**try/catch 對「hang」無效**（只擋 reject）。
- **修法＝伺服端注入 `window.__DATA`**：
  - Apps Script `doGet` 登入分支：UrlFetchApp 伺服端抓 records.json+watchlist.json（github.io）＋ EP 的 progress+needs，組成
    `window.__DATA={recs,watch,prog,needs}` 內嵌進 `<head>`（`</` 用 `String.fromCharCode(92)` 轉義防斷 script）。
  - index.html `boot()`：若見 `window.__DATA` 就直接用、**沙箱內不做任何跨域 fetch**；否則（公開版）照常 fetch。所有 fetch 加 `.catch` 保底。
- **代價**：登入版 doGet 做 4 次 UrlFetch，首屏 ~15-20s，會**先空白、再整頁一次跳出**——這是正常，不是壞掉。可優化（快取/減少 fetch）列待辦。

#### 10.3b 寫入路徑同樣中招（2026-08-13 下午修，**上次只修了讀取**）
- **上次的修法只處理 `boot()` 的讀取**，所有**寫入**仍是 client `fetch(EP)`：
  `setCat`／`saveProg`／`delProg`／`loadProg`／`saveNeed`／`loadNeeds`。
  因此登入版**點分類、記進度、刪進度、送需求單全部靜默卡死**——
  POST 其實有送出去（資料有寫進試算表），但接在後面的 `await loadProg()`（GET EP）hang 住，
  `renderAll()` 永遠不執行 → 畫面完全沒反應。
- **實證**：進度表出現兩筆同一分鐘的「進欣昱企業／設為交易洽談」＝點了沒反應又點一次。
- **修法**：index.html 新增 `epGet()／epPost()` 抽象層——
  `SANDBOX=!!(window.google&&google.script&&google.script.run)` 為真時走
  `google.script.run`（HtmlService 正規通道，不受跨域限制），由伺服端代打 EP；
  公開版 github.io 走原本的 `fetch`，行為不變。
- `openMd()` 也一併修：沙箱內相對路徑 `companies/*.md` 會指到 googleusercontent 抓不到，
  改走伺服端 `getMd()`，並補 `.catch` 保底（原本失敗會整個卡住不顯示）。
- **.gs 端新增三個函式**：`epGet(kind)` / `epPost(body)` / `getMd(file)`，
  全部用 UrlFetchApp 代打。原始碼備份於 repo `tools/appscript-sandbox-proxy.gs`。
- ⚠️ **鐵則：登入版沙箱內不得出現任何 client 端對 script.google.com 或相對路徑的 fetch。**
  日後新增任何會打 EP 的功能，一律走 `epGet`/`epPost`，不要再直接寫 `fetch(EP,...)`。
