## 🔴 本輪發現並修正的系統缺陷：MOPS 去重鍵用了不存在的欄位

9/19 的註記已指出「去重鍵不可用主旨、應用 `(COMPANY_ID, SPOKE_DATE, SPOKE_TIME)` 或完整 `HYPERLINK`」。
**本日實作時發現該修正方案本身也是錯的**：

`ezsearch_query` 回傳的欄位實際為
**`CDATE`／`CTIME`／`COMPANY_ID`／`COMPANY_NAME`／`SUBJECT`／`AN_NAME`／`AN_CODE`／`CODE_NAME`／`TYPEK`／`HYPERLINK`**，
**並沒有 `SPOKE_DATE`／`SPOKE_TIME` 這兩個欄位**（它們只出現在 `HYPERLINK` 的 query string 裡）。

用不存在的欄位當 key，`dict.get()` 全部回 `None`，去重鍵塌成 `(COMPANY_ID, None, None)`
＝**整批公告被壓成「一家公司一則」，同一天同一家發多則就只剩一則，且不會報錯**。
首次執行時 9/19 三個關鍵字合計 15 筆原始結果被壓成 2 則，就是這個原因。

**✅ 正解＝直接用完整 `HYPERLINK` 當去重鍵**（其 query string 內含
`SEQ_NO`＋`SPOKE_TIME`＋`SPOKE_DATE`＋`COMPANY_ID`，天然唯一）。

**已驗證**：改用 `HYPERLINK` 後重掃 9/18，
**玉山金(2884) 18:35:31 與 18:35:44 兩則同主旨重訊正確分列為 2 筆**
（即 9/19 被靜默合併、靠 C 線交叉比對才撈回來的那一組）。

> **教訓**：欄位名要從實際回應 dump 出來確認，不要沿用推測的名稱。
> 這類錯誤**不會拋例外、只會少資料**，是最難察覺的一種。
